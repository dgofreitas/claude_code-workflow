# Catalog — what exists here, and where

`S=.claude/skills/catalog/scripts/catalog.cjs` — the deterministic half. Agents write
entries; the script decides what a diff touched, what went stale, where two sub-projects
disagree on a contract, and renders `INDEX.md`.

## Boundary with `.claude/context/` — read this before writing anything

| | `.claude/context/` | `artifacts/catalog/` |
|---|---|---|
| Answers | **how** code must be written | **what** already exists here, and **where** |
| Nature | prescriptive, generic | descriptive, specific to this project |
| Owner | the workflow installer (overwritten on every upgrade) | the project repo (versioned, reviewed in the story's MR) |
| Read by | context-scout | architect, code-analyzer, catalog-keeper — via `$S lookup` |

- **Standards win for new code.** The catalog never prescribes. When existing code
  departs from a standard, its entry records that under **Desvios conhecidos** so nobody
  copies it as "the pattern" — extend the feature, follow the standard.
- **Never write the catalog under `.claude/`.** Reinstalling the workflow runs
  `rm -rf .claude/context`; anything project-specific there is lost on the next upgrade.
- context-scout does not read the catalog, and the catalog does not repeat standards.
- "catalog" may also be a word of the project's own domain (vislic has a *catálogo* of
  commercial items). The folder is `artifacts/catalog/`; a grep for `catalog` hits both —
  scope greps to `artifacts/catalog/` when you mean this one.

## Layout

```
$P/artifacts/catalog/
├── INDEX.md               GENERATED by `$S index` — never edit by hand
├── overview.md            the project in one screen: purpose, modules, neighbours, stack
├── features/<slug>.md     one per user-visible capability or internal subsystem
└── contracts/<slug>.md    one per interface this project PROVIDES or CONSUMES
```

## Entry format

### Feature — `features/<slug>.md`

The examples in this section come from a Node + Mongo pair (serverLic, vislic); the format is
the same for a C daemon, a Python API or a shell toolkit — only the kinds and names change.

```markdown
---
id: feature.sessions-v2-paging
type: catalog-feature
title: Paginação keyset das listas de sessões V2
summary: Listas activeSessions_V2/cloneSessions_V2 paginadas por cursor keyset sobre o Mongo
tags: [sessions, mongo, keyset, pagination]
files:
  - routes/v0/sessionsSnapshotPage.js
  - common/sessionsCursor.js
provides: [http.GET./licencaWeb/v0/activeSessions_V2]
consumes: [mongo.activeSessions]
stories: [STORY-012-sessoes-v2-mongo-keyset]
verified-at: af78a4a664
---

## O que faz
## Onde vive          file → symbol (function, class, export). NEVER line numbers — they rot.
## Decisões           one line each, pointing at the technical-analysis that made them
## Desvios conhecidos code that contradicts a .claude/context standard — do not copy it
## Armadilhas         what broke before, or will (only if real and non-obvious)
```

### Contract — `contracts/<slug>.md`

One file per **side**: serverLic's provider entry and vislic's consumer entry share the
same `id`, and that id is the join key `$S check` uses across sub-projects.

```markdown
---
id: http.GET./licencaWeb/v0/activeSessions_V2
type: catalog-contract
role: provider            # provider | consumer
kind: http                # see the kind table below
counterpart: vislic       # who is on the other side (consumer: who provides; via teco, external...)
title: GET activeSessions_V2
summary: Página de sessões ativas, cursor keyset, campos de sessão + host
tags: [sessions, http]
files:
  - routes/v0/admin.js
  - routes/v0/sessionsSnapshotPage.js
fields: [items, nextCursor, hostID, sessionID, status]
stories: [STORY-012-sessoes-v2-mongo-keyset]
verified-at: af78a4a664
---

## Forma              request (params, query, body) and response, as THIS side sees it
## Garantias          ordering, limits, error codes, auth — what the other side relies on
```

- **id** = `<kind>.<name>`, and `kind:` repeats the prefix. Any stack, any kind of boundary:

  | kind | name | examples |
  |---|---|---|
  | `http` | `<METHOD>.<full path as the wire sees it, :params kept>` | REST, GraphQL endpoint, webhook |
  | `rpc` | `<service>.<method>` | gRPC, XML-RPC, JSON-RPC |
  | `db` (or the engine: `mongo`, `postgres`, `redis`, `sqlite`…) | table / collection / key pattern | a table two services share |
  | `event` | channel, topic, queue, signal, SNMP trap | Pub/Sub, Kafka, AMQP, D-Bus |
  | `ipc` | socket path, port, pipe, shared memory | a daemon's Unix socket |
  | `lib` | public header / module / exported symbol | a C library's API, an SDK |
  | `cli` | command (+ subcommand) | a script other tools invoke |
  | `file` | path or pattern | a config another component overrides, a file one job writes and another reads |
  | `env` | VAR | set by compose/CI, read by the code |

  The name must be what BOTH sides can compute from their own code — for http that is the
  full path after every mount/prefix, for lib the symbol as declared in the public header.
  Pick the kind that names the boundary, not the technology behind it.
  The name must also be **unique across the umbrella**: two services each with a `sessions`
  collection are two contracts, so write `mongo.<database>.<collection>` (or `<schema>.<table>`,
  a key prefix…) whenever another project could own the same short name. `check` reports an
  ERROR when two projects provide one id.
- **fields**: provider = what it emits; consumer = what it actually READS (grep the
  consumer code, not the provider's docs). `$S check` reports `MISMATCH` when a consumer
  reads a field its provider does not emit.

### Rules for every entry

- `files:` is mandatory and lists every file the entry describes. It is what makes the
  entry go **stale** mechanically: `$S check` diffs those files from `verified-at` to HEAD.
- `verified-at:` = short sha of the commit whose code you actually read.
- `stories:` = inline list (the artifact hook turns it into Obsidian links).
- Write the body in the language of the project's stories. Target ≤ 80 lines per entry.
- One feature per entry. A file may appear in several entries; an entry never spans
  unrelated capabilities just to cover files.
- Do not catalogue tests, build files or artifacts. `overview.md` may extend the default
  ignore list with an `ignore:` block list of globs (e.g. `crontab/filesLic/**`).

### overview.md

Frontmatter: `type: catalog-overview`, `verified-at:`, optional `ignore:`. Body: purpose
(3 lines), module map (dir → one line), neighbours (who calls us, whom we call, through
what — e.g. "vislic → teco (proxy, allowlist scopeRoutes) → serverLic"), stack, how to run.

## Commands

| Command | What it does |
|---|---|
| `node $S lookup --project $P <terms…>` | entries matching the terms, best first (≤8) |
| `node $S affected --project $P [--base <ref>]` | what the branch's diff touched — first line `CATALOG: update` or `CATALOG: no-op` |
| `node $S check --project $P [--siblings d1,d2]` | ERROR / MISMATCH / STALE / INFO, exit 2 on any non-INFO |
| `node $S index --project $P` | rewrite INDEX.md (refuses while there are ERRORs) |
| `node $S inventory --project $P` | bootstrap map: files per dir with line counts, routes, env, collections |
| `node $S summary --project <dir>` | one line per catalogued project with stale entries, nothing when all is current — run by the SessionStart hook; covers every sub-project from an umbrella root |

`lookup` marks every stale result inline (`⚠ STALE since <sha>: <files>`), because the
moment someone reads an entry to plan is when a stale one does harm — before any story has
had the chance to refresh it.

## Mode: init (first time)

Run from the main session. Never in the sub-project checkout's own branch — use a
dedicated branch (`docs/catalog-bootstrap`), so the bootstrap lands as one reviewable MR.

1. `node $S inventory --project $P` → split the source into **batches of ≤ 8 files or
   ≤ 1500 lines**, one directory (or one coherent subsystem) per batch. Cost grows with the
   files per delegation, so never hand one agent a whole repo. The inventory's interface
   hints (routes, env, ipc, api, http-out, tables…) are heuristics per language — a stack it
   has no patterns for still gets its files and line counts, which is enough to batch by.
2. Write `overview.md` first (one catalog-keeper call: inventory + build manifest + README).
3. **The callers' side first.** Collect what calls this project's interfaces: the
   `http-out`, `rpc`, `ipc`, `lib` lines of every sibling's `inventory` (umbrella) AND of this
   project's own tools — a tester, a load bot, cron scripts living in the same repo are
   callers too. Resolve prefixes the inventory leaves as `${VAR}`. Hand each batch the list of
   those interfaces whose implementation lands in it, so it writes them as provider contracts
   with the counterpart named. Without this a batch cannot know which of its interfaces anyone
   uses, and the consumers end up with no provider to be checked against.
4. **Ask how many batches run at once** — unless the user's request already named a number.
   Parallelism does not change the total cost, only how fast it is spent: N batches cost the
   same 2 or 20 at a time, but 20 at once can exhaust a plan's usage window in one go (the
   serverLic/vislic pilot did, twice), while a few at a time spread the spend and let the
   window roll over mid-run. Only the user knows their plan and what else they need it for
   today. Use AskUserQuestion, with the measured numbers in the question itself:

   > "N lotes para catalogar <projeto> (~$1,20 e 5–10 min por lote, medido no piloto —
   > ~$<N×1,2> no total em preço de API). Quantos em paralelo?"

   | Option | Description |
   |---|---|
   | `Todos (até 20)` | ~<⌈N/20⌉ × 8> min; for plans with headroom (Max 20x and up) |
   | `8` | ~<⌈N/8⌉ × 8> min |
   | `4` | ~<⌈N/4⌉ × 8> min; spreads the spend on a 5x-class plan |
   | `2` | slowest; for a day the plan is still needed for other work |

   Say in the question that **the choice does not change quality**, only speed and plan
   pressure — measured on the pilot: each batch has its own context, so running it next to 19
   others reads the same code the same way. What parallel batches cannot do is see each
   other's in-flight writes, and every race that produces is caught deterministically
   before `index` accepts the catalog: two providers of one id, or two features providing
   one contract → ERROR; a response assembled across batches → MISMATCH, resolved in
   finalize. That is why step 5 is never skipped, at any parallelism.

   Then dispatch in waves of that size — start the next batch as each one returns:
   `Mode: init. Project: $P. Batch: <files>. Neighbours: <from overview>. Interfaces others
   use from this batch: <list from step 3>. Verified-at: <sha>.`
   **A batch cut off by a usage limit is resumed, never restarted:** its writes are on disk,
   so after the reset send that same agent a message (SendMessage) to continue. Restarting
   from zero pays for the batch twice.
5. One `catalog-keeper` call in `Mode: finalize` — it runs `index` and `check` and fixes the
   ERRORs. This session writes nothing itself: the main session is a router (Master's
   NEVER-write rule), and `index` writes a file. STALE is impossible right after init; if it
   shows, a batch read a different commit.
6. Report: entries per kind, coverage %, MISMATCH/INFO list. Do NOT commit unless the
   user asked for it.

## Mode: check

`node $S check --project $P`. Relay the output as printed. STALE entries → offer a
catalog-keeper call in `Mode: refresh` with exactly those entries. In an umbrella, a
sibling's catalog still on an unmerged branch lives in a worktree — pass it with
`--siblings <worktree dir>` or its contracts read as "no provider catalogued".

## Mode: lookup

`node $S lookup --project $P <terms>` and relay. Read an entry only if asked.
