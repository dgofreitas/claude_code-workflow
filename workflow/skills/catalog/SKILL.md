# Catalog — what exists here, and where

`S=.claude/skills/catalog/scripts/catalog.cjs` — the deterministic half. Agents write
entries; the script decides what a diff touched, what went stale, where two sub-projects
disagree on a contract, and renders `INDEX.md`.

## Boundary with `.claude/context/` — read this before writing anything

| | `.claude/context/` | `artifacts/catalog/` |
|---|---|---|
| Answers | **how** code must be written | **what** already exists here, and **where** |
| Nature | prescriptive, generic | descriptive, specific to this project |
| Owner | the workflow installer (overwritten on every upgrade) | the project repo (versioned, reviewed in the story's MR) |
| Read by | context-scout | architect, code-analyzer, catalog-keeper — via `$S lookup` |

- **Standards win for new code.** The catalog never prescribes. When existing code
  departs from a standard, its entry records that under **Desvios conhecidos** so nobody
  copies it as "the pattern" — extend the feature, follow the standard.
- **Never write the catalog under `.claude/`.** Reinstalling the workflow runs
  `rm -rf .claude/context`; anything project-specific there is lost on the next upgrade.
- context-scout does not read the catalog, and the catalog does not repeat standards.
- "catalog" may also be a word of the project's own domain (a store's *catálogo* of
  products). The folder is `artifacts/catalog/`; a grep for `catalog` hits both —
  scope greps to `artifacts/catalog/` when you mean this one.

## Layout

```
$P/artifacts/catalog/
├── INDEX.md               GENERATED by `$S index` — never edit by hand
├── overview.md            the project in one screen: purpose, modules, neighbours, stack
├── features/<slug>.md     one per user-visible capability or internal subsystem
└── contracts/<slug>.md    one per interface this project PROVIDES or CONSUMES
```

## Entry format

### Feature — `features/<slug>.md`

The examples in this section come from a Node + Mongo pair (an `api` and the `web` GUI that
consumes it); the format is the same for a C daemon, a Python API or a shell toolkit — only
the kinds and names change.

```markdown
---
id: feature.sessions-paging
type: catalog-feature
title: Paginação keyset da lista de sessões
summary: Lista de sessões paginada por cursor keyset sobre o Mongo
tags: [sessions, mongo, keyset, pagination]
files:
  - routes/v1/sessionsPage.js
  - common/sessionsCursor.js
provides: [http.GET./api/v1/sessions]
consumes: [mongo.app.sessions]
canonical:
  - "cursor keyset da lista → common/sessionsCursor.js#encodeCursor — opaco, base64 de JSON v3"
stories: [STORY-012-sessoes-keyset]
verified-at: af78a4a664
---

## O que faz
## Onde vive          file → symbol (function, class, export). NEVER line numbers — they rot.
## Fonte canônica     each domain value or rule this feature owns → the ONE symbol that computes
                      it, and the test that pins it. Then "Cópias conhecidas": other places that
                      compute the same thing (they diverge — treat as debt, never as a second source).
## Decisões           one line each, pointing at the technical-analysis that made them
## Desvios conhecidos code that contradicts a .claude/context standard — do not copy it
## Armadilhas         what broke before, or will (only if real and non-obvious)
```

### Contract — `contracts/<slug>.md`

One file per **side**: the `api`'s provider entry and the `web`'s consumer entry share the
same `id`, and that id is the join key `$S check` uses across sub-projects.

```markdown
---
id: http.GET./api/v1/sessions
type: catalog-contract
role: provider            # provider | consumer
kind: http                # see the kind table below
counterpart: web          # a label for people: who is on the other side
title: GET /api/v1/sessions
summary: Página de sessões ativas, cursor keyset, campos de sessão + host
tags: [sessions, http]
files:
  - routes/v1/router.js
  - routes/v1/sessionsPage.js
fields: [items, nextCursor, hostID, sessionID, status]
stories: [STORY-012-sessoes-keyset]
verified-at: af78a4a664
---

## Forma              request (params, query, body) and response, as THIS side sees it
## Semântica          per field whose meaning a name does not carry: unit, scale, currency,
                      time zone / instant vs civil day, which date, what a record represents
## Garantias          ordering, limits, error codes, auth — what the other side relies on
```

- **id** = `<kind>.<name>`, and `kind:` repeats the prefix. Any stack, any kind of boundary:

  | kind | name | examples |
  |---|---|---|
  | `http` | `<METHOD>.<full path as the wire sees it, :params kept>` | REST, GraphQL endpoint, webhook |
  | `rpc` | `<service>.<method>` | gRPC, XML-RPC, JSON-RPC |
  | `db` (or the engine: `mongo`, `postgres`, `redis`, `sqlite`…) | table / collection / key pattern | a table two services share |
  | `event` | channel, topic, queue, signal, SNMP trap | Pub/Sub, Kafka, AMQP, D-Bus |
  | `ipc` | socket path, port, pipe, shared memory | a daemon's Unix socket |
  | `lib` | public header / module / exported symbol | a C library's API, an SDK |
  | `cli` | command (+ subcommand) | a script other tools invoke |
  | `file` | path or pattern | a config another component overrides, a file one job writes and another reads |
  | `env` | VAR | set by compose/CI, read by the code |

  The name must be what BOTH sides can compute from their own code — for http that is the
  full path after every mount/prefix, for lib the symbol as declared in the public header.
  Pick the kind that names the boundary, not the technology behind it.
  The name must also be **unique across the umbrella**: two services each with a `sessions`
  collection are two contracts, so write `mongo.<database>.<collection>` (or `<schema>.<table>`,
  a key prefix…) whenever another project could own the same short name. `check` reports an
  ERROR when two projects provide one id.
- **fields**: provider = what it emits; consumer = what it actually READS (grep the
  consumer code, not the provider's docs). `$S check` reports `MISMATCH` when a consumer
  reads a field its provider does not emit.
- **A proxy or gateway** that forwards a family of interfaces is ONE provider contract with a
  wildcard id: `*` in the name, or `ANY` as the http method (`http.ANY./api/v1/*`).
  A consumer behind it keeps the FINAL provider's id and never names the hop: `path` deduces
  it (a wildcard provider in a third project covering the id). `counterpart:` is a label for
  people; no script reads it, so the route never depends on its wording.

### Rules for every entry

- **Canonical sources are the point.** The defect this catalog exists to prevent is not a rule
  changed on purpose — it is the same domain rule (a position, an exchange rate, a currency
  map, a cache key, a date window) computed again somewhere else, the copies drifting apart,
  and a fix that patches one copy. Measured on an installed project: 16 of 22 knowledge-gap
  bugs that reached production. So every value or rule an entry owns goes in `canonical:` (frontmatter,
  `"<what> → <file>#<symbol>"`) and under **Fonte canônica**, and every other place that
  computes it goes under **Cópias conhecidas** — with the file, so the next story can route
  it to the source. `lookup` prints `canonical:` first.
- **A mirror of another sub-project's rule says whose.** When this code deliberately repeats a
  rule a sibling owns (a GUI pre-validating what the API will enforce), its `canonical:` line
  ends with `espelho de <projeto>:<arquivo>#<símbolo>@<sha>` — the owner's symbol and the
  owner's commit this copy was compared against. The symbol may be a dotted key path in a data
  file (`#roles.client.web`); an owner with no symbol — a document — is named by file alone
  (`espelho de api:docs/GLOSSARY.md@<sha>`), and goes STALE when that file changes. Written once, on the mirror's side; the
  owner's `lookup` shows "espelhado por" by computing it. `check` fails when the owner's symbol
  is gone and marks the mirror STALE when the owner's file changed since that sha: a rule fixed
  on one side of the umbrella and not on the other is the drift this catches. Example, in a
  `web` sub-project mirroring its `api` sibling:
  `"limite do nome → src/forms/name.js#parseName — trim, sem controle, ≤ 80 code points; espelho de api:src/names.js#normalizeName@1a2b3c4d5e"`
- **Semantics travel with the value.** Each `canonical:` line ends with ` — <semantics>`
  whenever the value's name does not say it all, and contracts carry a **Semântica** section.
  Write it for: numbers with a unit or scale (percent vs decimal, cents vs units), money
  (which currency), dates and times (instant vs civil day stored as 00:00 UTC, which time
  zone, which date — event, record, settlement, payment), and records whose kind is not
  obvious (a live reading vs a historical one in one collection). Measured on the same project:
  the contract bugs that reached production were all of this kind — both sides agreed on the
  field's name and type and disagreed on its meaning (a rate in percent read as decimal, a
  civil day shown one day early in local time, one kind of date deduplicated against another).
  Shape-only checks cannot see them; only the written meaning can.

- `files:` is mandatory and lists every file the entry describes. It is what makes the
  entry go **stale** mechanically: `$S check` diffs those files from `verified-at` to HEAD.
- `verified-at:` = short sha of the commit whose code you actually read.
- `stories:` = inline list (the artifact hook turns it into Obsidian links).
- Write the body in the language of the project's stories. Target ≤ 80 lines per entry.
- One feature per entry. A file may appear in several entries; an entry never spans
  unrelated capabilities just to cover files.
- Do not catalogue tests, build files or artifacts. `overview.md` may extend the default
  ignore list with an `ignore:` block list of globs (e.g. `scripts/legacy/**`).

### overview.md

Frontmatter: `type: catalog-overview`, `verified-at:`, optional `ignore:`. Body: purpose
(3 lines), module map (dir → one line), neighbours (who calls us, whom we call, through
what — e.g. "web → gateway (proxy, route allowlist) → api"), stack, how to run.

## Commands

| Command | What it does |
|---|---|
| `node $S lookup --project $P <terms…>` | entries matching the terms, best first (≤8); under each, the route of its interfaces through the sibling sub-projects with what each hop handles, and "espelhado por" when a sibling mirrors a rule it owns |
| `node $S path --project $P <terms…\|id>` | the route of an interface across the umbrella: who consumes it, the hops it passes through (deduced wildcard providers), who provides it — and under every hop, the `canonical:` rules handled there. Computed on each call, never stored |
| `node $S path --project $P --to <id>` | who reaches an interface, two levels up — the impact of changing it |
| `node $S affected --project $P [--base <ref>]` | what the branch's diff touched — first line `CATALOG: update` or `CATALOG: no-op` |
| `node $S check --project $P [--siblings d1,d2]` | ERROR / MISMATCH / STALE / INFO, exit 2 on any non-INFO. Besides the contract cross-check: a feature that `provides:` what this project's own contract says it consumes (ERROR), and every `espelho de` reference (owner symbol gone → ERROR, owner changed since its sha → STALE). INFO `possible undeclared mirror` for a `canonical:` line naming a sibling next to copy wording with no `espelho de` — a heuristic: refresh the entry and let the keeper decide |
| `node $S index --project $P` | rewrite INDEX.md (refuses while there are ERRORs) |
| `node $S inventory --project $P` | bootstrap map: files per dir with line counts, routes, env, collections |
| `node $S summary --project <dir>` | one line per catalogued project with stale entries, nothing when all is current — run by the SessionStart hook; covers every sub-project from an umbrella root |
| `node $S check --project <ROOT>` | from an umbrella root: fetches, then one block per sub-project — a header with where its checkout stands (branch, behind/ahead its integration branch, clean or not) and that project's check, with its own `(remedy)` line |
| `node $S plan --project <ROOT\|P>` | what refresh/init would do, one line per item: `SYNC <name> <base> <n>` (checkout safely fast-forwardable), `WARN <name> <state>`, `REFRESH <name> <base> <entry…>`, `INIT <name> <base> <why>`, then `PLAN: …` |
| `node $S sync --project <ROOT> [names…]` | fast-forwards the checkouts that are clean, on their integration branch and only behind it; prints `SYNCED` / `SKIPPED <why>`. Never switches a branch, never touches a dirty or diverged checkout |
| `node $S prepare --project <ROOT>/<name> --branch <b> [--base <ref>]` | fetches and creates (or reuses) the worktree `<ROOT>/.worktrees/<name>-<last segment of b>` on branch `b` from the integration branch; prints `WORKTREE <path> <branch> <sha>` |

`lookup` marks every stale result inline (`⚠ STALE since <sha>: <files>`), because the
moment someone reads an entry to plan is when a stale one does harm — before any story has
had the chance to refresh it.

## Scope: umbrella root, a named sub-project, or named entries

`/sdlc:catalog <mode> [<sub-projeto>] [<entradas>…]`. The scope comes from the arguments, never
from a question the user did not need:

| Arguments | Scope |
|---|---|
| a sub-project name first (a directory of the umbrella) | that sub-project, **for this command only** — the session's active sub-project is not changed |
| none, in an umbrella | `check`, `refresh` and `init` cover the whole umbrella (below); `lookup`/`path` use the session's active sub-project, or ask |
| none, single project | `$P` |
| entries after the name | exactly those entries |

**State first, at the root.** `check`, `refresh` and `init` without a sub-project start with
`node $S plan --project <ROOT>` (it fetches). `SYNC` lines → ask ONCE, listing them: "N
repositórios estão só atrás da branch de integração, limpos — atualizar (fast-forward)?". Yes
→ `node $S sync --project <ROOT> <names>`, relay `SYNCED`/`SKIPPED`, then re-run `plan`. Never
switch a branch, pull a dirty checkout or touch one on another branch — a checkout on a story
branch may be another session's work in progress; `WARN` lines say so, and are relayed as they
are. Refresh and init do not depend on it: they write in fresh worktrees (`prepare`).

## Mode: init (first time)

**At the root, no sub-project named:** after the state step, the `INIT` lines are the
candidates. Ask which (AskUserQuestion, multiSelect, one option per `INIT` line with its
reason) — never init them all unasked: init is the costliest operation, done once per project.
A catalog that exists only on the remote is a `SYNC`/`WARN`, never an `INIT`: rebuilding it
pays for one that already exists. Then, per chosen sub-project, one at a time: `node $S
prepare --project <ROOT>/<name> --branch docs/catalog-bootstrap`, `$P` = the printed worktree,
and the steps below.

Run from the main session. Never in the sub-project checkout's own branch — use a
dedicated branch (`docs/catalog-bootstrap`), so the bootstrap lands as one reviewable MR.

1. `node $S inventory --project $P` → split the source into **batches of ≤ 8 files or
   ≤ 1500 lines**, one directory (or one coherent subsystem) per batch. Cost grows with the
   files per delegation, so never hand one agent a whole repo. The inventory's interface
   hints (routes, env, ipc, api, http-out, tables…) are heuristics per language — a stack it
   has no patterns for still gets its files and line counts, which is enough to batch by.
2. Write `overview.md` first (one catalog-keeper call: inventory + build manifest + README).
3. **The callers' side first.** Collect what calls this project's interfaces: the
   `http-out`, `rpc`, `ipc`, `lib` lines of every sibling's `inventory` (umbrella) AND of this
   project's own tools — a tester, a load bot, cron scripts living in the same repo are
   callers too. Resolve prefixes the inventory leaves as `${VAR}`. Hand each batch the list of
   those interfaces whose implementation lands in it, so it writes them as provider contracts
   with the counterpart named. Without this a batch cannot know which of its interfaces anyone
   uses, and the consumers end up with no provider to be checked against.
4. **Ask how many batches run at once** — unless the user's request already named a number.
   Parallelism does not change the total cost, only how fast it is spent: N batches cost the
   same 2 or 20 at a time, but 20 at once can exhaust a plan's usage window in one go (the
   first pilot did, twice), while a few at a time spread the spend and let the
   window roll over mid-run. Only the user knows their plan and what else they need it for
   today. Use AskUserQuestion, with the measured numbers in the question itself:

   > "N lotes para catalogar <projeto> (~$1,20 e 5–10 min por lote, medido no piloto —
   > ~$<N×1,2> no total em preço de API). Quantos em paralelo?"

   | Option | Description |
   |---|---|
   | `Todos (até 20)` | ~<⌈N/20⌉ × 8> min; for plans with headroom (Max 20x and up) |
   | `8` | ~<⌈N/8⌉ × 8> min |
   | `4` | ~<⌈N/4⌉ × 8> min; spreads the spend on a 5x-class plan |
   | `2` | slowest; for a day the plan is still needed for other work |

   Say in the question that **the choice does not change quality**, only speed and plan
   pressure — measured on the pilot: each batch has its own context, so running it next to 19
   others reads the same code the same way. What parallel batches cannot do is see each
   other's in-flight writes, and every race that produces is caught deterministically
   before `index` accepts the catalog: two providers of one id, or two features providing
   one contract → ERROR; a response assembled across batches → MISMATCH, resolved in
   finalize. That is why step 5 is never skipped, at any parallelism.

   Then dispatch in waves of that size — start the next batch as each one returns:
   `Mode: init. Project: $P. Batch: <files>. Neighbours: <from overview>. Interfaces others
   use from this batch: <list from step 3>. Verified-at: <sha>.`
   **A batch cut off by a usage limit is resumed, never restarted:** its writes are on disk,
   so after the reset send that same agent a message (SendMessage) to continue. Restarting
   from zero pays for the batch twice.
5. One `catalog-keeper` call in `Mode: finalize` — it runs `index` and `check` and fixes the
   ERRORs. This session writes nothing itself: the main session is a router (Master's
   NEVER-write rule), and `index` writes a file. STALE is impossible right after init; if it
   shows, a batch read a different commit.
6. Report: entries per kind, coverage %, MISMATCH/INFO list. Do NOT commit unless the
   user asked for it.

## Mode: check

`node $S check --project $P` — or, at the root with no sub-project named, the state step and
then `node $S check --project <ROOT>`. Relay the output as printed. Each `(remedy)` line names
the entries to refresh — STALE ones (a STALE mirror included: the refresh compares the copy
with the owner again and moves its `@sha`), ones breaking a rule, and `possible undeclared
mirror` ones (the keeper decides whether the copy is a sibling's rule and declares it). Offer
that refresh, per sub-project, as written in the line. In an umbrella, a sibling's catalog
still on an unmerged branch lives in a worktree — pass it with `--siblings <worktree dir>` or
its contracts read as "no provider catalogued".

## Mode: refresh

Re-verify entries against the code without waiting for them to go stale — after an entry is
found wrong, or after the keeper's rules changed (e.g. provider fields now come from what the
code writes). One `catalog-keeper` call in `Mode: refresh` with exactly the entries named —
`providers` expands to every `role: provider` contract; batch them (≤ 15 entries per call),
in parallel like init. Then `check`. Do not commit unless the user asked.

**No entries named** — the entries are the ones `plan` lists, decided by the script, not by
reading entries:

1. The state step (above), then `node $S plan --project <ROOT or P>`. No `REFRESH` line →
   say so and stop.
2. At the root: show the `REFRESH` lines (sub-project → entries) and ask which sub-projects
   (AskUserQuestion, multiSelect, `Todos` first). A sub-project named in the arguments skips
   the question. Then the parallelism question of init step 4, with N = Σ⌈entries/15⌉ calls.
3. Per chosen sub-project: `node $S prepare --project <ROOT>/<name> --branch docs/catalog-refresh`
   — never write in the checkout. `$P` = the printed worktree; the keeper calls get
   `Mode: refresh. Project: $P. Entries: <the REFRESH line's entries, ≤ 15 per call>`.
   Different sub-projects are different repos: their calls run in parallel safely, and their
   worktrees share one branch name, so each one's check sees the others' in-flight entries.
4. `node $S check --project $P` in each worktree, relay, report the branch per sub-project.

## Mode: lookup

`node $S lookup --project $P <terms>` and relay. Read an entry only if asked.

"por onde passa X" / "quem chega em X" → `node $S path --project $P <terms|id>` (or `--to <id>`)
and relay. In an umbrella it reads every sibling's catalog by itself.
